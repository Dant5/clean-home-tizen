# Daily Bing wallpaper reliability

The old launcher treated the TV's calendar day as proof that Bing had published that day's image. A valid but still-old en-AU response after local midnight set `BING.date` to the new local day; hourly checks then skipped all requests until another day or forced event. This can leave yesterday's photograph on screen after Bing later publishes a replacement.

The fix reuses the existing hourly timer. While visible in Photo + Daily Bing mode, it revalidates the archive about hourly even after success, keeping Bing's `startdate` and image identity separately from the local date. Same-image responses do not advance the successful wallpaper-change timestamp. Older publication responses cannot replace a newer known daily image. Local date is used for manual-photo next-day reset, not to certify provider publication. Markets can publish on a different schedule from local midnight; no fixed Bing publication SLA is assumed.

Archive requests use a fresh request query and fetch `cache: no-store` (fresh query also covers the Chromium 63 XHR fallback). Image URLs remain identity-based and cacheable; unchanged photos are not needlessly decoded/downloaded again. Failed requests/decode keep the previous working image or bundled fallback. Failure backoff is 15 minutes; the next existing hourly/resume/online event retries when due. Successful checks are limited to approximately hourly, with one local-day crossing check; repeated wake/reconnect events cannot create request bursts. Explicit user changes can request immediately. A clock correction backwards does not lock the gate indefinitely.

Suspended TVs cannot fetch. The existing resume, visibility and online handlers check when eligible; a TV that unloads the app recovers saved URL/identity candidates without blocking startup. Cached URLs must decode before being displayed. A manually selected Bing image remains selected through hourly daily-image checks and same-day restart; it resets at the next TV-local day once a valid replacement can be shown. A failed replacement preserves the working image rather than blanking the screen.

## Local diagnostic

In the launcher's local developer console, `ShoreQA.bing()` returns selected/daily image identity (including full Bing image IDs), provider publication date, last successful wallpaper change/check/failure timestamps, local date, timezone offset, market and manual-pick day. Times are milliseconds since epoch (`new Date(value).toISOString()` converts them). This read-only diagnostic is not added to automatic reports or sent anywhere. No TV connection is required to use it in the local preview.

Timezone/configuration on the physical television was not queried or changed. If investigating there later, check its displayed date/time and timezone privately; Perth is UTC+8 year-round. A correct TV clock cannot fix late provider publication by itself. Internet loss, standby, CDN metadata caching and image/decode failures are separate causes handled by the above retry/fallback paths. The observed Bing response on 8 November supplied `startdate`, `fullstartdate` and an identity URL; these fields do not establish a universal publication time.

## Verification scope

`npm run check:bing` runs existing manual-choice UI tests plus mocked publication regressions in UTC and Australia/Perth: late publication, stale archive, cache controls, manual next-day reset, decode failure, bounded resume/online retries and offline restart. `npm test` also exercises hidden/visible timer behavior, legacy network timeout handling, Home/input regressions and resource bounds. Existing GitHub push/PR Actions run production tests in current Chromium/85 and packaged compatibility engines 63/69/76/85/94/108/120/130. No nightly builds or additional Dell job is needed.

Browser success does not prove physical Samsung Home-button interception, boot/startup replacement, firmware compatibility, standby events or live Bing network/CORS behavior. Those require an approved owner-observed test. This change does not modify Home/native helpers, startup routing, firmware settings, launcher identity, favourites or other launcher features.

## Later installation and rollback (not performed)

1. Before a separately approved TV installation, identify its currently installed version privately. Save the exact current signed widget, checksums and own-app preferences using the established recovery procedure. Preserve matching author certificates outside Git and confirm the affected encrypted recovery copy on Hubert. Do not assume the older documented 1.3.8 stable widget is the current installation.
2. Review the tested source change and assign a release version through the existing release process. Build/sign only the ordinary widget with the existing owner's author identity; keep app `D5Q60BHome.CleanHome`, package `D5Q60BHome`. The test artifact is unsigned/generic and is not an install-ready signed release. Keep new and previous artifacts distinct, checksum both and check package contents/tests.
3. Use the established same-author **in-place own-app update**, without uninstalling or rerunning Home/startup setup. Do not write Home routing, firmware, Last App or other applications' data. Follow [installation guide](INSTALL.md); do not invoke setup transactions merely to refresh the wallpaper code.
4. Owner checks saved favourites/appearance and short/long Select, Home and ordinary startup/standby behavior; then inspects the local diagnostic across a late publication/wake. Verify the actual new image identity when available. No deliberate power interruption or firmware change is needed.
5. If regression occurs, use the saved same-author previous widget and documented in-place recovery. Added Bing metadata fields are backward-compatible with the old saved URL/date fields. If the installer rejects a version downgrade, stop and use a reviewed recovery package of the previous source under an accepted version; **do not uninstall, reset Smart Hub or overwrite native routing** to force recovery. Keep the existing native inverse-recovery procedure for separately approved emergencies, not this ordinary update.

The private legacy repo's `docs/STABLE-BASELINE.md` and `docs/Q60B-INSTALL.md` preserve the last documented frozen widget and native rollback evidence. Their frozen baseline remains untouched. No physical TV was contacted, modified or deployed to for this fix.
